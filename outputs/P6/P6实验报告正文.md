# 第六章 知识融合与知识图谱构建

本章以项目2实体、项目3路线及项目5扩展抽取结果为输入，在P6中完成线路质量筛选、历史时间汇总、条件推荐归集、实体主题摘要及Neo4j实际入库。正式交付图谱覆盖广州长隆、九寨沟和珠海长隆，共6763个节点、9824条关系，包含29个线路候选、115个具体交通路段、217组历史时间汇总及265组条件推荐汇总；其中257个实体与景区组合已由LLM生成548条主题摘要，归属249个唯一实体ID。项目5原始产物保持不变；本章正式数量均来自清理后的release及实际数据库验证，不沿用清理前的218个线路对象统计。

## 6.1 输入关联与融合策略

原始语料共47篇，包括41篇游客游记和6篇官方资料。官方与游客知识使用同一景区注册表和实体ID关联，保留来源类别、文本编号、原文范围及抽取观测，不因来源不同重复建立同一注册实体，也不将官方来源直接等同于当前仍有效的事实。

| 输入文件 | 关联键 | 在融合中的用途 |
| --- | --- | --- |
| processed/P1爬虫数据清洗/documents.json | doc_id、原文范围 | 原文、标题、来源及精确片段核对 |
| processed/P2实体识别/entities.json | scenic_code、entity_id、mention_id | 景区内规范实体及逐次提及关联 |
| processed/P3路线层级挖掘/routes.json | route_id、step_id、entity_id | 继承基础路线、步骤、顺序和实体引用 |
| processed/P5条件建议抽取/runs/full-final-20261101/integrated/ | entity_id、route_id、step_id、observation_ids | 原始图、线路、路段、属性与条件建议；时间汇总由P6重建 |
| processed/P6知识图谱/cleaned-v1/ | 节点id、关系两端id | 二次清理后唯一正式图谱及对象表 |

POI按景区区分实体，名称相同但景区不同不自动合并；交通方式使用跨景区共享ID。实体ID用于对齐同一对象，mention_id用于定位不同提及，observation_ids用于追踪不同抽取记录。来源合并保留全部观测引用；本组未训练置信度模型，也未将提及频次包装成概率置信度。父区域与子景点保持独立，只有原文明示的所属关系才建立PART_OF。

项目5存在的主要缺失是线路粒度不统一：局部安排、单地点活动和交通片段与较长行程共同输出为ROUTE。清理前共有218个线路对象、774个步骤，不能据此声称拥有218条完整推荐路线。本组没有回写或重跑P5，而是在P6新增clean_routes.py，依据原文、顺序及行程范围独立分类，再生成正式入库文件。

处理顺序为：读取冻结的P5输出；回查P1原文范围；诊断有序地点阶段；区分长序列、专题行程、跨园概要与片段；检查精确重复和片段归属；移出不合格线路及其步骤；清理遗留作用域绑定；重建历史时间汇总；归集同一实体的条件与建议；调用LLM生成主题标签及自然语言内容；生成图谱与审计文件；验证后导入Neo4j。线路筛选和时间、建议归集采用程序规则；主题摘要使用已完成的真实模型输出，离线重建直接读取冻结结果。

时间汇总程序及结果已由P5迁入P6，线路筛选、时间汇总和条件推荐汇总共同作为入库前的质量处理。P5负责逐条抽取与关联，原始抽取观测不回写。时间汇总按对象、时间用途、景区及作用域归组，保留原文表达及条件；对可明确解析的区间求并集，无法解析的自然语言时间仍保留，不因格式不统一丢弃。

条件推荐先无损归集，再生成主题摘要。第一层读取1358条条件规则及112条相关属性，共1470条原始记录；按实体、景区和作用域形成265组汇总。多目标记录可进入多个实体组，因此1816次目标归属不等于1816条独立建议；仅合并1次明确重复，保留1815个归集条目。265组中有6组无明确实体目标，另有2组带被排除片段作用域；这些组保留审计信息，均不进入默认实体主题摘要。未定位建议的景区标签只说明来源，不能当作对全景区普遍适用。

第二层将257个有效实体与景区组合分别发送给deepseek-flash，同一实体按实际内容生成“主题标签＋自然语言内容”，例如预约与入园、适合人群、交通与顺序、餐饮等。模型可以在一个主题下写多句话，保留条件、建议、禁止或要求语气及联合目标；不强制把全部信息压成一句。每个主题携带原始条目和记录ID，由程序校验引用存在性及覆盖率，再挂回原实体。共获得548条主题摘要，涉及249个唯一实体ID；通用交通方式跨景区共享ID，因此实体与景区组合数大于唯一ID数。该处理汇总条件、建议及112条相关属性，并未对全部480条FACT做全面属性摘要。

真实联调共发出262次非流式模型请求，包含修复请求，不能将请求数直接当作实体数。上下文上限为30000 token；记录中的实际平均输入为1443.5 token、平均总用量为1618.7 token，最大输入为9243 token、最大总用量为11023 token。所有主题均保留“历史资料记载”的表述；结构与引用覆盖已校验，不据此声称每个摘要均已完成独立语义复核。

最终移出189个线路对象，保留29个。广州长隆由98个降至11个，九寨沟由84个降至8个，珠海长隆由36个降至10个。单次出现或低频本身不是排除依据，180个POI、34个通用交通方式、115个交通路段全部保留。

精确重复要求同文章、同景区及完整步骤内容一致，本批未合并精确重复线路。片段归属要求同文章、原文范围包含、地点顺序匹配且父候选唯一，本批没有可靠归属成立；15对同文章顺序子序列仅列为待确认候选，不生成归属边，不跨文章拼接。29个候选仍可能有语义近重复，尚未完成全面语义去重。

移出片段时同时检查属性、条件及路段绑定，产生201项作用域处理记录。失效route_id或step_id清空后，原值保存在upstream_*字段，并标注scope_status=excluded_route_fragment_scope；失效目标转存审计字段。不能因为route_id变为空，就把片段属性提升成全景区事实。默认推荐查询应排除该作用域。原始OBSERVATION保留为证据，不作为有效线路绑定。此前时间归类与条件语义疑点没有在本轮全面修正。

## 6.3 图谱模式设计

图谱以稳定ID标识对象，共十种语义节点。具体交通路段连接两个地点，通用交通方式只表达“步行、缆车、高铁”等类别，不具有固定起终点。线路通过步骤表达顺序，不能将步骤相邻直接视为存在交通服务。

| 节点类型 | 标识 | 数量 | 主要属性 |
| --- | --- | --- | --- |
| POI | entity_id | 180 | name、scenic_code、role、subtype |
| TRANSPORT | entity_id | 34 | 通用交通方式名称 |
| TRANSPORT_LEG | leg_id | 115 | from_entity_id、to_entity_id、transport_entity_id、连接性质 |
| ROUTE | route_id | 29 | 简介、人群、p6_curation分类及范围、原文证据 |
| ROUTE_STEP | step_id | 344 | index、poi_ids、transport_ids、time、order_group、原文 |
| FACT | 图内稳定id | 480 | attribute、value_text、condition、modality、作用域 |
| CONDITIONAL_RULE | rule_id | 1358 | 条件、后果、语气、表达类型及目标 |
| TIME_SUMMARY | time_summary_id | 217 | 原文时间集合、条件、结构化区间、历史性标记 |
| ADVICE_SUMMARY | advice_summary_id | 265 | 实体与景区、条件推荐条目、作用域、主题结果与来源引用 |
| OBSERVATION | observation_id | 3741 | 工具名、输入包、来源doc_id及原文块范围 |

POI属性包括所属园区、开放时间、预约要求、进入限制、停留或行程时间等；路段属性包括乘坐时长、运行时间、班次、费用及限制，均按原文保留。480个FACT由375条POI属性和105条交通属性组成；没有原文依据的字段不补值。条件建议使用独立节点，以APPLIES_TO连接实体、路段或线路；不能定位目标的条件允许独立保存。

| 关系 | 方向 | 数量 | 语义 |
| --- | --- | --- | --- |
| HAS_STEP | ROUTE→ROUTE_STEP | 344 | 线路包含步骤 |
| PRECEDES | ROUTE_STEP→ROUTE_STEP | 324 | 上游支持的步骤先后，保留无序组 |
| VISITS | ROUTE_STEP→POI | 325 | 步骤涉及地点，非新增交通服务 |
| MENTIONS_MODE | ROUTE_STEP→TRANSPORT | 38 | 步骤中提及交通方式 |
| USES_LEG | ROUTE→TRANSPORT_LEG | 13 | 线路有证据使用具体路段 |
| FROM | TRANSPORT_LEG→POI | 115 | 路段起点 |
| TO | TRANSPORT_LEG→POI | 115 | 路段终点 |
| USES_MODE | TRANSPORT_LEG→TRANSPORT | 112 | 路段方式；三段方式未明示 |
| HAS_FACT | POI或TRANSPORT_LEG→FACT | 480 | 对象具有属性观测 |
| HAS_TIME_SUMMARY | 对象→TIME_SUMMARY | 217 | 对象对应时间集合 |
| HAS_ADVICE_SUMMARY | 对象→ADVICE_SUMMARY | 259 | 对象对应条件推荐汇总；无实体目标组不建此边 |
| DERIVED_FROM | ADVICE_SUMMARY→原始规则或属性 | 1816 | 汇总追溯到原始记录；不是独立建议条数 |
| PART_OF | POI→POI | 64 | 原文明示的隶属关系 |
| APPLIES_TO | CONDITIONAL_RULE→目标对象 | 1204 | 条件或建议作用对象 |
| SUPPORTED_BY | 业务对象→OBSERVATION | 4398 | 来源观测支持 |

Neo4j另使用P5Node作为技术公共标签，十类统计不把公共标签另计为语义类型。217组时间汇总中，41组属于可用时间，48组含多来源观测；可明确解析的区间进行并集，其他表达以带条件的自然语言集合保留。时间表示来源当时的记录，不代表当前仍开放，也不表示集合之外必然关闭。不同来源的矛盾或历史变化不能由求并集自动消除。

548条主题以advice_themes附着于所属实体，并在对应ADVICE_SUMMARY保存llm_theme_result；主题没有另建548个节点。实体主题中的label、summary、scenic_code及source_record_ids分别用于显示主题、阅读内容、过滤景区和追溯依据；详细主题结果另保留scope_bindings等适用范围信息。Neo4j将嵌套属性保存为advice_themes_json等JSON字符串，查询后由程序解析。

## 6.4 构建实现与结构化输出

正式入口为processed/P6知识图谱/release.json，dataset为p6-quality-themes-v1-1bae9157a9a3，对应cleaned-v1/graph.json。清理前图谱为7117个节点、9311条关系；最终版本为6763个节点、9824条关系。仅完成线路筛选的中间版本为6498个节点、7749条关系；最终版本在该基础上增加265个条件推荐汇总节点与2075条归属和追溯关系，并在原实体附加主题摘要。数量变化同时反映线路移出及派生汇总增加，不能据此替代语义质量评估。

cleaned-v1同时输出routes.json、entities.json、transport_legs.json、conditions.json、entity_time_summaries.json、condition_recommendation_summaries.json及entity_advice_theme_summaries.json。route_decisions.csv/json列出全部218个对象的判断，route_fragments_audit.json保存189个排除对象，scope_cleanup_audit.json保存作用域调整，route_relationship_candidates.json保存尚未确认的15对候选。上述审计对象不作为正式线路导入。

统一构建入口为src/P6知识图谱/quality_pipeline.py，顺序执行线路筛选、时间汇总、条件推荐归集和已验证主题结果绑定；clean_routes.py只输出线路筛选中间结果，summarize_advice_llm.py负责模型汇总与断点续跑；src/P6知识图谱/run.py执行prepare和import，命令行只接受四阶段完成、输入及图谱哈希核验通过的图，阻止直接把未清理P5图入库。导入使用dataset和id定位节点、确定性关系键匹配边；复杂嵌套字段序列化为JSON属性，读回时还原核对。release指定的同名目录保存import_bundle.json、validation.json、live_verification.json、cleaned_queries.json和queries.cypher。

实际数据库导入前，先备份旧项目快照，再导入清理后数据并验证，验证通过后移出旧快照。数据库当前项目只保留清理后的dataset；重复导入不增加节点或关系。旧快照备份位于仓库外个人资源归档，正式入库不混用旧路线。源图SHA256为f459a3af480475cd3e22d7607b40cc6c73e07d14d9e6f6cad242bfa63be53ec7。
